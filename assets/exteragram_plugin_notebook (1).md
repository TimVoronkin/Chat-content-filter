# ExtraGram: разборы плагинов и приёмы разработки

Этот конспект собирает выводы из присланных пользователем плагинов. Разделяем то, что видно в исходниках, предполагаемый результат на телефоне и ограничения конкретной реализации. При разборе не меняем исходный плагин и не считаем наличие кода доказательством его работоспособности на любой сборке.

## 01. chaTools 2.1 — инструменты в поле ввода чата

Источник: присланный файл `chaTools (2).plugin`, 2350 строк.

Автор в метаданных: `@exoseo -> @HzzzPlugins`. ID: `chatools`. Заявлены приложение от 12.5.1 и SDK от 1.3.3.3. Эти значения — декларация автора, не результат проверки совместимости.

SHA-256 исходника: `641e06a8f06b7582481124c105c6279f23094397b7b5f756eb2ae16db951a672`.

Статус исследования: весь исходник прочитан, выполнен статический разбор. Отдельно выполнена только изолированная функция разбиения строки `_frames`; плагин, Android-код и отправка сообщений не запускались. Проверки на телефоне нет.

### Функции, доступные пользователю

| Элемент | Реальное поведение по коду |
| --- | --- |
| Кнопка возле поля ввода | Одна дополнительная кнопка с иконкой из ресурсов клиента. Открывает собственную панель с двумя переключателями. |
| «Анимация набора текста» | Отправляет начало текста, затем дописывает оставшийся текст серией редактирований того же сообщения. Это изменение содержимого сообщения, а не статус «печатает…». |
| «Исчезающие сообщения (1 сек)» | Заменяет текст отправленного сообщения на обычный дефис `-`. Вызовов удаления сообщения или настройки TTL в файле нет. |
| Сочетание режимов | Сначала пытается показать текст частями, затем заменить его на дефис. |
| Индикация | Иконка кнопки меняет цвет, когда включён хотя бы один режим. |
| Настройки | Оба режима выключены по умолчанию. Сохраняются глобально, без отдельных настроек на чат или аккаунт. |
| Приветственное окно | Предлагает вручную открыть канал автора `HzzzPlugins`; выбор сохраняется через `welcome_shown`. `create_settings()` возвращает пустой список. |

Анимация содержит максимум пять кадров. Проверенный пример для «Привет»: `П` → `Пр` → `Прив` → `Приве` → `Привет`. Первый кадр отправляется исходным сообщением; следующие кадры — запросы редактирования. В коде заданы интервалы 0,15–0,18 секунды, но ожидание ответов и очереди может их увеличить. Доставка серверных изменений не гарантирует отображение каждого промежуточного кадра на другом устройстве.

Таймер исчезновения считается от начала `_execute()` после получения серверного ID, а не от прочтения собеседником. В сочетании с анимацией полная фраза может оставаться видимой значительно меньше секунды. Замена текста не является гарантией уничтожения уже полученных копий.

`on_send_message_hook()` обрабатывает непустой строковый `params.message`; пропускает повторные отправки через `retryMessageObject` и отложенные сообщения с `scheduleDate`. Текст обрезается через `strip()`. При подстановке первого кадра очищаются `entities`, поэтому форматирование может теряться. Наличие хука `sendMedia` не означает поддержку удаления вложений.

Полезный принцип: подтверждение принятия сообщения сервером ищется несколькими путями. Это позволяет не путать факт вызова отправки с появлением окончательного `message_id`. Предпочтительные ключи связи — аккаунт, диалог, `random_id`, локальный и серверный ID. Сравнение только текста — менее надёжный запасной вариант.

### Отправка и редактирование: поток данных

1. `on_send_message_hook` создаёт словарь задания с аккаунтом, диалогом, полным текстом, кадрами и режимами.
2. При анимации в `params.message` подставляется первый кадр; возвращается `HookStrategy.MODIFY`.
3. Java-хук, NotificationCenter, ответы на запросы и серверные updates пытаются определить ID отправленного сообщения.
4. `_kick()` запускает `_execute()` после появления положительного серверного ID и защищает от повторного запуска флагом `kicked`.
5. `_edit()` выбирает прямой запрос `TL_messages_editMessage` либо SDK-функцию `edit_message()` с MessageObject.
6. В прямом запросе устанавливаются текст и `no_webpage`. `_refresh_local_row()` дополнительно обновляет объекты сообщения и адаптер списка на устройстве отправителя.
7. При `autodel` вызывается `_hide_msg()` с текстом `-`.

Отдельно: локальная замена `messageOwner.message`, элементов `messages` и `notifyDataSetChanged()` меняет отображение у отправителя. Подтверждением изменения на сервере она не является.

### Недостатки, которые не стоит переносить

1. **Ложное подтверждение успеха.** `_edit()` возвращает `"ok"` даже после неудачи обоих способов. `_edit_via_tl()` после ожидания 1,2 секунды не проверяет, что callback действительно пришёл; отсутствие ответа может считаться успехом. `_edit_via_helper()` подтверждает успешный вызов функции, не серверный результат.
2. **Поглощение ошибок.** Статически найдено 157 обработчиков исключений, заканчивающихся `pass`. Внешне функция может молча не работать. Нужны ограниченное логирование и явные статусы ошибок.
3. **Текст отправляется частично до завершения задания.** Если дальнейшие правки не пройдут, у собеседника может остаться лишь первый фрагмент. Форматирование очищается, разбиение по кодовым точкам может разрезать составные эмодзи.
4. **Нет корректного ожидания FLOOD_WAIT.** Код замечает подстроку `FLOOD`, но использует фиксированные короткие задержки, а не указанное сервером время ожидания.
5. **Слабые запасные способы сопоставления.** Некоторые ветви выбирают сообщение по совпадению текста или первый ожидающий job данного аккаунта. Поиск в открытом фрагменте не везде проверяет диалог и аккаунт; одинаковые сообщения и смена чатов повышают риск неправильного сопоставления.
6. **Общая очередь и активное ожидание.** `_ensure_waiter()` может ждать до 14 секунд с шагом 20 мс внутри `run_on_queue`; рядом в ту же очередь ставятся другие задачи. Это может задерживать исполнение. Опрос положения панели каждые 32 мс тоже избыточен при отсутствии изменений.
7. **Неполная отмена при выгрузке.** Хуки и подписки снимаются, но нет общего флага остановки запущенных jobs и задач повторного подключения. Уже поставленные задачи могут продолжить работу. Layout-listener панели явно не снимается при закрытии.
8. **Нет сохранения незавершённых заданий.** `_jobs` существует только в памяти. При добавлении новых заданий старые отбрасываются по возрасту, список ограничен 32 элементами. Завершение после остановки процесса не обеспечивается.
9. **Версионная совместимость требует проверки.** Используются `get_messages_controller(account)`, `get_notification_center(account)`, `get_send_messages_helper(account)` и `send_request(..., account=...)`. В имеющихся официальных stubs SDK 1.4.3.8 такие параметры у этих функций отсутствуют, в актуальной документации присутствуют. Это основание проверить вызовы в пользовательской сборке 1.4.3.3, а не утверждать её полную несовместимость по одному сравнению.

### Выводы для следующих разработок

Использовать как образец встраивания кнопки в панель ввода, работы с темой, привязки панели к клавиатуре и получения ID сообщения через несколько событий. Логику редактирования, определения успешного результата, аккаунтов и отмены задач переносить только после исправления перечисленных проблем.

На основе приёма можно сделать панель шаблонов, преобразование набранного текста, перевод, быстрые действия, управление форматированием или инструменты для вложений. Это направления новых разработок, а не дополнительные функции chaTools.

## 02. iOS Circle 3.2 — плавная смена камеры в видеокружках

Источник: присланный файл `IOS circle.plugin`, 4006 строк. Автор в метаданных: `@exoseo -> @HzzzPlugins`, ID `ios_circle`. Заявлены приложение от 12.5.1 и SDK от 1.3.3.3. Заявленный минимум SDK сам по себе не подтверждает совместимость всех внутренних методов клиента.

SHA-256 исходника: `281e4fe15fe973dbcd2ff47cda1802630c7c0eacd56e355fea163e9529227206`.

Статус: прочитан Python-код, извлечён и статически разобран встроенный DEX: список классов и методов, Dalvik-инструкции и декомпиляция основных алгоритмов. DEX — 19 332 байта, формат 035, SHA-256 `7416ef62df9dd4fb88b08a22594870efb075f78ff967b12a2e28c1769a465cbd`. Проверена отдельно извлечённая чистая функция `_mix_ms`, без импорта плагина. Плагин, DEX и Android-код не запускались; проверки на телефоне нет. Псевдокод декомпилятора не является исходным Java: в частности, он местами показывает битовые представления float как целые числа. Выводы о численных коэффициентах сверялись с инструкциями.

### Что происходит с кружком

Главный эффект создаётся обработкой записанного файла перед отправкой. Хуки камеры запоминают начало записи и моменты переключения; в найденном коде они не реализуют отдельную плавную анимацию живого видоискателя. Переход, если обработка успешна, становится частью самого видео и виден получателю.

1. Хуки `InstantCameraView` и связанных компонентов определяют начало записи, смену камеры, остановку, паузу и отмену. Python сохраняет времена переключений относительно начала записи.
2. В `ChatActivity.sendMedia`, делегате камеры или `SendMessagesHelper.prepareSendingVideo…` находится файл кружка. Принадлежность определяется по `VideoEditedInfo.roundVideo` либо ранее запомненному пути.
3. Плагин сохраняет исходный метод, объект и аргументы; `param.setResult(None)` откладывает нормальную отправку. По возможности отменяется уже начатая загрузка исходного файла.
4. В фоновой задаче ожидается завершение записи файла, затем создаётся `<имя>_iosmix.mp4` в кэше.
5. Основной DEX-модуль уточняет переходы по содержимому кадров. Он удерживает кадр со старой камеры и постепенно смешивает его с новыми кадрами. Это crossfade: обе камеры одновременно снимать не требуется.
6. Видеодорожка перекодируется в H.264; аудиодорожка копируется с временными метками. Ошибки копирования звука не во всех ветках делают весь результат неуспешным.
7. Плагин подменяет путь вложения, обновляет связанные поля `VideoEditedInfo` и продолжает исходный вызов отправки на UI-потоке. При ошибке обработки предусмотрена попытка отправить оригинал.

Практическая цена — задержка перед отправкой, обработка всего ролика, нагрузка на устройство и возможное изменение качества. Наличие резервной ветки не гарантирует успешного результата на любом наборе кодеков.

### Настройки и реальное поведение

| Настройка | Что видно в реализации |
| --- | --- |
| Длительность | В меню 250, 320, 380, 450, 550, 700 мс; по умолчанию 380 мс. При числовом индексе 0 выбор 250 мс ошибочно превращается в 380 мс. |
| Кривая перехода | Linear, iOS style, Ease-in-out. При числовом индексе 0 Linear ошибочно превращается в iOS style. Кривые DEX и Python различаются даже при одном названии режима. |
| Auto | Сначала DEX, при неуспехе резервный Python-проход с подбором кодека. |
| DEX (flagship) | Только DEX-обработка; при её ошибке результатом обычно становится отправка оригинала. Название не доказывает использование GPU для смешивания. |
| Compatibility | Тоже сначала пробует DEX; отличается предпочтениями кодеков в резервной ветке. |
| Software | Пропускает DEX-обработку видео и предпочитает программные кодеки. Однако запасной `createEncoderByType` не гарантирует выбор именно программного кодека. |
| Reload DEX | Сбрасывает и загружает обработчик заново; также сбрасывает часть состояния диагностики и превью. |
| Debug | Локальные логи, просмотр и копирование, запись сведений об устройстве, кодеках и установленных хуках. Автоматическая отправка этих логов в Python-коде не найдена. |
| Превью | Готовый GIF, загружаемый с `i.ibb.co` и сохраняемый в кэше. Он не пересчитывается из выбранной длительности и easing. |

Причина ошибок первого пункта селектора — `int(self.get_setting("mix_duration", 2) or 2)` и аналогичное `or 1` для easing. В Python ноль считается ложным. Изолированная проверка `_mix_ms` дала: индексы 0–5 → 380, 320, 380, 450, 550, 700. Для значения по умолчанию надо отдельно проверять `None`, сохраняя допустимый индекс 0.

`_on_mix_setting()` пуст. В файле есть функции анимационного превью, включая `_start_mix_anim`, но найденный путь отображения загружает готовый GIF; вызовов `_start_mix_anim` нет. Наличие вспомогательной функции не означает, что пользовательская функция подключена.

### Что находится внутри DEX

Три класса: `ioscircle.Mixer`, `Mixer$MuxState`, `Mixer$1`. Основные публичные методы: `run(String, String, String)`, `process(String, String, int, boolean, int)`, `processWithCuts(String, String, int, boolean, int, long[])`, `describeCuts(String)`.

`run` разбирает строку вида `mixMs=380;freeze=1;easing=1;cuts=1500,3000` и вызывает `processWithCuts`. `process` вызывает тот же обработчик без заранее известных переключений. `describeCuts` — заглушка, возвращающая пустую строку.

Внутренний `detectCuts` принимает **семь параметров**: `MediaExtractor`, `MediaFormat`, ширину, высоту, длительность, длительность смешивания и `ArrayList`. Он декодирует видео, получает яркостные миниатюры 16×16 и сравнивает соседние кадры. Если переданы времена из хуков, ищет подходящую смену изображения в окне примерно от −900 до +400 мс от каждого времени. Если времён нет, пробует искать сильные перепады автоматически. Такой детектор может реагировать на резкое движение или смену освещения: это анализ картинки, а не доказательство физического переключения камеры.

Затем видео декодируется для обработки ещё раз. На переходе используется сохранённый кадр со старой камеры; DEX также пытается выбрать стабильный кадр перед скачком. RGB-компоненты смешиваются с меняющимся весом. Переход может сокращаться, если рядом следующая склейка или конец видео. Результат снова преобразуется в YUV, кодируется в H.264 и собирается в MP4 вместе с копией аудио.

Смешивание реализовано циклами по пикселям, без найденных OpenGL/EGL-вызовов. Сам `MediaCodec` может выбрать доступный системный кодек; слово «flagship» в настройке не означает отдельный GPU-шейдер.

В DEX easing 1 — smoothstep `t²(3−2t)`, easing 2 — кубическая ease-in-out; в Python используются кривые Безье `(0.25, 0.1, 0.25, 1.0)` и `(0.42, 0, 0.58, 1)`. Поэтому при переходе между движками форма эффекта может отличаться.

### Ошибки и ограничения, которые не стоит переносить

1. **Потеря нулевого значения селектора.** Подтверждено изолированной проверкой: `or default` ломает 250 мс и Linear при числовом индексе 0.
2. **Несовпадение интерфейса детектора.** Python `_dex_detect_cuts` ищет `detectCuts` с 1–3 аргументами, а во вложенном DEX он имеет 7. Эта внешняя попытка получить список склеек не работает с данным модулем. Сам DEX всё же вызывает свой детектор из `processWithCuts`, поэтому основная обработка не лишена автоопределения.
3. **Неподключённый резервный детектор.** `_py_detect_cuts` определён, но не вызывается. Сообщение лога «still trying py detect» не подтверждает его работу. При пустом списке склеек Python-ветка способна просто перекодировать видео без переходов и сообщить об успехе.
4. **Демонстрация не соответствует настройкам.** Превью — готовый GIF; изменение параметров не показывает пользователю рассчитанный результат.
5. **Общее состояние записи.** `_rec_start` и `_switches_ms` общие для экземпляра плагина. Фоновая обработка берёт переключения позднее, поэтому начало следующей записи потенциально может повлиять на предыдущее задание. Лучше фиксировать независимое задание: аккаунт, файл, временные метки и параметры.
6. **Паузы и быстрые переключения.** Времена считаются по часам устройства; явного вычитания длительности пауз нет. Отсечение повторов минимум примерно 450–520 мс может удалить настоящее быстрое переключение. DEX пытается уточнить времена по картинке, но это не полноценная замена корректной временной шкале.
7. **Контекст аккаунта.** Отмена загрузки использует `UserConfig.selectedAccount`, а не обязательно аккаунт исходной записи. Для нескольких аккаунтов его нужно сохранять вместе с заданием.
8. **Недостаточная проверка результата.** Успех во многом определяется отсутствием ошибки и непустым выходным файлом. В Python-проходе есть предел 90 секунд, а итоговая проверка не требует подтверждения полного конца потока. Возможный неполный ролик надо проверять по длительности, завершению кодека и сохранности звука перед отправкой.
9. **Неоднозначность форматов пикселей.** Есть предположения о расположении YUV, в том числе для flexible-формата. Корректные цвет и геометрия требуют проверки на реальном кодеке, а не только успешного запуска `MediaCodec`.
10. **Ожидание и отмена.** Результат `_wait_stable` не используется как обязательное условие обработки. В фоне нет общего механизма отмены задания при выгрузке плагина. Явного обхода `_unhooks` при выгрузке не найдено; автоматическую очистку самим SDK нужно проверять отдельно.

Это описание найденного поведения, не гарантия безопасности всей среды клиента.

Поведение Android API в этом разделе восстановлено по присланному исходнику и встроенному байткоду. Повторная внешняя сверка документации в этой сессии была недоступна из-за ошибки сервиса поиска. Этот пример расширяет набор изученных приёмов: можно вмешиваться в жизненный цикл записи, задерживать отправку вложения, обрабатывать локальное видео средствами Android, вызывать встроенный DEX из Python и затем возвращать управление штатной отправке.

### Подключение ИИ и передаваемые данные

Нужен собственный API-ключ OpenRouter. Запросы идут на `https://openrouter.ai/api/v1/chat/completions` через `urllib.request` с обычной проверкой TLS, таймаутом 45 секунд и `max_tokens=800`. История диалога, текущее входящее сообщение, дата/время, системная инструкция и пожелания пользователя собираются в одну строку `content` с ролью **system**. Внешнему сервису отправляется именно этот текст, поэтому обработка истории не ограничивается телефоном.

В `MODEL_CHAIN` записаны, по порядку:

1. `nvidia/nemotron-3-ultra-550b-a55b:free`;
2. `inclusionai/ling-3.0-flash:free`;
3. `openai/gpt-oss-120b:free`;
4. `nvidia/nemotron-3-super-120b-a12b:free`;
5. `openrouter/free`.

Это содержимое файла, не утверждение о доступности моделей или условиях сервиса сегодня. Константы `DEFAULT_MODEL` и `FLASH_MODEL` отдельно не используются. Интерфейс показывает часть ключа, а сам ключ сохраняется через `set_setting`; собственное шифрование ключа в файле не реализовано.

Базовый промпт просит отвечать коротко, имитировать стиль и ошибки, редко использовать эмодзи, не раскрывать автоматическую природу ответа, иногда промолчать. Большинство таких ограничений — просьбы модели, а не обязательные проверки кода. `call_ai` дополнительно заменяет ё на е и удаляет длинные тире, повторяет запрос при наличии `send_at` внутри текста ответа, а при ответе длиннее 100 слов просит сократить его до 20. Результат повторного запроса не проходит весь исходный набор преобразований повторно.

### Точная логика инициативы

Поток `initiate_loop` просыпается каждые 300 секунд. Для одного чата попытка проверки ограничена одним разом в час, а создание новой инициативы допускается между 10:00 и 22:59 местного времени. Это ограничение времени проверки, не повторная проверка времени непосредственно перед отправкой: предложенный ИИ таймер может перенести отправку на более поздний час. Для обычных ответов такого программного ночного запрета нет.

Интервал между инициативами вычисляется по активности: 2, 4 или 8 часов. Базовый шанс 3%; добавляются 2 процентных пункта при недавнем входящем и 3 при активности менее двух часов назад без накопленных игнорирований. За каждый счётчик игнорирования вычитается 5 пунктов; в будние дни с 09 до 18 часов шанс дополнительно уменьшается вдвое с округлением вниз. Время последней ручной исходящей реплики пользователя отдельно не учитывается в `last_any`: там используются входящая активность и `last_ai_activity`.

Если модель вернула непустую инициативу, проверяется, писал ли собеседник после предыдущей. Предусмотрены значения паузы 12, 24 и 48 часов. Но счётчик обновляется уже после случайного допуска и генерации; текущая новая инициатива всё равно планируется. При продолжающемся молчании после первого увеличения счётчика шанс может стать нулевым, поэтому наличие трёх ветвей паузы не означает, что они последовательно отработают.

Поля **«Шанс первым (%)»** и **«Интервал (мин)»** сохраняются как `initiate_chance` и `initiate_interval`, но в `initiate_loop` не читаются. Они не управляют описанной логикой. Выставить нулевой шанс в этом поле — не надёжный способ запретить инициативу.

### События, таймеры и работа в фоне

Регистрируются `TL_updateNewMessage`, `TL_updateNewChannelMessage`, `TL_updateShortMessage`, `TL_updateShortChatMessage`, `TL_updates`, `TL_updatesCombined`, `TL_updateShort`. Возвращается обычный `HookResult`: исходящее сообщение создаётся отдельным вызовом, а входящее не заменяется и не блокируется.

Дополнительно `watcher_loop` опрашивает локальную таблицу сообщений. Общий шаг — 5 секунд; заданный интервал для открытого чата 6 секунд означает на таком шаге примерно 10 секунд между проверками, для остальных — 30 секунд. При первой проверке последний ID просто запоминается. Это резервное обнаружение новых записей в уже доступной локальной базе, не отдельная непрерывная серверная сессия.

Генерация выполняется в Python-потоках, отложенные действия — в `threading.Timer`. На время API-запроса и отправки предпринимается попытка взять `PowerManager.PARTIAL_WAKE_LOCK` максимум на 60 секунд и затем освободить его. Это временное удержание CPU; в файле нет отдельного Android foreground service, системного расписания или восстановления очереди отправок после перезапуска процесса. Работа 24/7 из наличия wake lock не следует.

### Подтверждённые недостатки и ограничения

1. **Отмена read/typing-таймеров написана неверно.** В `cancel_scheduled` для `read_timer` и `typing_timer` повторно вызывается `timer.cancel()`. Изолированная проверка показала: send отменён, read и typing остались активны. Если send-таймера уже нет, попытка вызова у `None` также просто подавляется.
2. **Выключение AI не отменяет уже запланированную отправку.** `toggle_chat` только сохраняет флаг. Отправляющий callback повторно не проверяет `enabled` или `is_running`. Ручной ответ владельца аккаунта тоже не отменяет ожидающий автоматический ответ. Даже удаление чата не останавливает уже выполняющийся API-запрос: после его завершения может появиться новое задание.
3. **Параметры инициативы не используются**, а диапазон задержки обычного ответа перекрывается правилом 15–40 секунд. В тесте запрошенные 300 секунд превратились в 25 секунд. Это задержка после получения ответа от модели, а не полное время от входящего сообщения.
4. **Знакомая проблема Java ArrayList.** `on_updates_hook` делает `for up in inner_updates` без запасного `size()/get(i)`. В среде, где Java ArrayList не является Python iterable, обработка контейнера прервётся, а пустой `except` скроет ошибку. Нельзя утверждать, что конкретно на телефоне пользователя это случилось, но код уязвим к уже встречавшейся несовместимости.
5. **Слабая дедупликация и потеря новых вводных.** Хук не обновляет `last_message_ids`, используемый watcher. Пока чат в `processing_chats`, новые сообщения сразу пропускаются, без очереди. Обработка одной реплики двумя путями или ответ по устаревшему контексту зависят от порядка событий.
6. **Аккаунты смешаны в состоянии.** Чаты, кэш, таймеры и блокировки индексируются только `dialog_id`. Входящий hook получает аккаунт, но `get_messages_storage()` и `send_text()` вызываются без него, а фоновые циклы берут `UserConfig.selectedAccount`. Совпадение контекста, адресата и аккаунта требует исправления или проверки в конкретном SDK.
7. **Кэш не учитывает аккаунт и глубину.** TTL 30 секунд, ключ только чат; новый входящий текст добавляется к запросу отдельно, но прежний контекст может остаться устаревшим. Запросы с разными limit могут получить один и тот же кэшированный результат.
8. **Неструктурированный ответ может уйти в чат.** Если JSON не распарсился, `parse_json` делает весь текст модели полем `response`. Проверки `send_at` и длины не гарантируют, что вместо реплики не будут отправлены пояснения, отказ или служебный текст. Имитированная «причина» из `reasoning` — лишь возвращённое поле, не проверяемое объяснение работы модели.
9. **Переписка помещается в системную инструкцию.** Текст собеседника и история не отделены самостоятельными сообщениями от правил. Вложенные в переписку инструкции могут повлиять на генерацию; отдельной проверки результата перед автосендом нет.
10. **Ограничения истории и участников.** SQL берёт доступные локальные записи, до фильтрации пустого текста и объединения ролей. В группы не передаются отдельные имена участников. Поиск последнего входящего смотрит только последние 15 записей и может его не найти после серии своих сообщений.
11. **Время и валидация.** `parse_time` трактует прошедшее сегодня время как отправку через 5 секунд, не завтра; для обычного ответа затем применяется минимум 15 секунд. В настройках чата нет проверки `min <= max` и диапазона процентов. Системное тихое время для ответов отсутствует, остаётся просьба в промпте.
12. **Ошибки интерфейса и журналов.** Функция `prompt_dialog` для глобального System Prompt есть, но из меню не вызывается. В `chat_settings` создан ScrollView, однако в диалог передаётся сам LinearLayout без добавления в ScrollView; длинная форма может не прокручиваться. Запись логов несколькими потоками не синхронизирована. Сохранение настроек и «отправлено» могут показываться без подтверждения фактического результата.

### Выводы для будущих разработок

Новые полезные приёмы: чтение истории прямо из локального Telegram-хранилища, десериализация TL-объектов, объединение событий и резервного опроса, отправка typing/read-событий, внешний LLM API, планирование действий и кратковременный wake lock.

На этой основе можно разрабатывать помощника с черновиками ответов, генератор вариантов формулировки, сводки последних сообщений, перевод по контексту или ответы для выбранных рабочих чатов. Для автоматической отправки необходимы корректная отмена, изоляция аккаунтов и заданий, строгий формат ответа и повторная проверка новых сообщений перед отправкой. Изученные функции не следует считать готовым надёжным автопилотом без этих доработок.

По описанию автора и сообщению пользователя возвращает привычное открытие списка диалогов при нажатии нижней кнопки пересылки. Реализация `ChatActivity.openForward` в самом файле отсутствует; внешняя сверка исходников клиента была недоступна из-за ошибки сервиса поиска. ### Единственная функция и механизм

При загрузке плагин находит конкретный Java-метод и ставит хук:

```python
ChatActivity.getClass().getDeclaredMethod("openForward", Boolean.TYPE)
```

В `before_hooked_method` выполняется одна операция:

```python
param.args[0] = True
```

Следовательно, каждый перехваченный вызов именно `ChatActivity.openForward(boolean)` получает первый аргумент `True`, независимо от исходного значения. Метод затем продолжает обычное выполнение: `setResult`, замены реализации и собственного рисования панели нет. Наблюдаемый пользователем результат — открытие привычного варианта пересылки — достигается изменением входного условия уже существующего кода клиента.

В файле нет создания `View`, новых кнопок, изменения LayoutParams, обработчиков нажатия, анимации, сетевых запросов, таймеров или собственных настроек. Это один приём изменения поведения интерфейса. Панель и собственно пересылку обслуживает клиент.

### Что изучаем для других плагинов

| Элемент | Точное значение в примере | Применение |
| --- | --- | --- |
| Прямой доступ к Java-классу | `from org.telegram.ui import ChatActivity` | Можно работать с классом клиента из Python, если он доступен в данной среде. |
| Reflection по сигнатуре | `getDeclaredMethod("openForward", Boolean.TYPE)` | Находит метод с конкретным именем и типом аргумента; это не перехват всех перегрузок `openForward`. |
| Примитивный тип Java | `Boolean.TYPE` обозначает `boolean` | В reflection важно отличать примитивный `boolean` от объектного `java.lang.Boolean`. |

Основной принцип: прежде чем создавать собственную панель, полезно исследовать, какие режимы и компоненты уже есть в клиенте и какой метод выбирает нужный вариант. Возможные направления применения — выбор существующего диалога, режима меню, вкладки или параметра анимации. Это направления поиска: наличие подходящих флагов для каждого такого случая необходимо проверять по реализации клиента.

### Границы и область воздействия

1. **Нет проверки источника вызова.** Хотя описание говорит о нижней кнопке пересылки, хук не проверяет, какая кнопка была нажата. Он меняет все перехваченные вызовы выбранного метода. Возможны изменения других путей, которые используют ту же сигнатуру.
2. **Нет фильтра по чату или аккаунту.** Поведение не ограничено конкретным `ChatActivity`, диалогом или учётной записью.
3. **Зависимость от внутренней реализации.** Должны совпасть класс, имя метода, параметр `boolean` и смысл `True`. Указанный в метаданных минимум версии не заменяет эту проверку.
4. **Жизненный цикл оставлен SDK.** В файле нет `on_plugin_unload`, сохранения объекта unhook или явного снятия хука. По одному этому файлу нельзя заключить, остаётся ли хук после выключения: нужно знать автоматическую очистку SDK.
5. **Существующая панель должна присутствовать в клиенте.** Подмена аргумента сама по себе не восстанавливает код интерфейса, который был полностью удалён из приложения.

Для будущей выборочной модификации можно исследовать контекст `param.thisObject` и условия вызова, чтобы применять подмену только в нужном чате или сценарии. В данном плагине таких условий нет.

## 05. AntiAyugramDelete 1.2 — попытка изменить текст перед удалением

Источник: `AntiAyugramDelete (1).plugin`, 324 логические строки (323 перевода строки). Автор `@exoseo -> @HzzzPlugins`, ID `antiayugramdelete`; заявлены приложение от 12.5.1 и SDK от 1.4.3.3. SHA-256: `a423ef9204797607a8fac129d81729928d3088284766e8496f3905ab625c2019`.

### Вердикт по обещанию

Код не подтверждает обещание «клиенты AyuGram других людей не прочитают удалённые сообщения». Плагин отправляет обычные запросы редактирования перед штатным удалением. Он не получает доступ к хранилищу другого устройства, не определяет клиент собеседника и не посылает специальную команду очистки истории AyuGram.

Официальный README AyuGram4A описывает сохранение истории сообщений отдельно от обычного кэша, а также синхронизацию истории через AyuSync. Если исходная версия уже сохранена независимо, последующее редактирование серверного сообщения не доказывает уничтожение этой версии. Конкретное отображение зависит от сборки получателя, настроек сохранения и порядка получения обновлений.

Возможный ограниченный эффект: клиент, сохраняющий только последнюю версию сообщения и успевший применить правку, может показывать заменённый текст. Это условный сценарий, не измеренный результат и не гарантия защиты от AyuGram.

### Реальная последовательность

1. `hook_all_methods` устанавливает `DeleteHook` на перегрузки `MessagesController.deleteMessages`.
2. До выполнения штатного удаления хук предполагает, что `args[0]` содержит Java-список ID сообщений, а `args[3]` — ID диалога. ID из списка читаются через `size()` и `get(i)`.
3. `_protect_messages` выбирает peer и `ConnectionsManager` для `UserConfig.selectedAccount`.
4. Для каждого сообщения генерируется текст из ASCII-символов и переносов строк, обрезанный до 3900 символов. Добавляются обычные Telegram entities для жирного, курсива, кода, зачёркивания или подчёркивания — примерно 20 фрагментов при стандартной длине.
5. Отправляется первый `TL_messages_editMessage`. Несмотря на название `OVERWRITE_ITERATIONS`, в этой версии значение равно **1**.
6. После двух локальных пауз по 0,05 секунды отправляется второй `TL_messages_editMessage` с фиксированным текстом **`[пошол нахуй с ауграмом :3]`**, оформленным entity `Pre` как блок кода.
7. После обработки всех ID выполняется ещё `sleep(0.1)`, затем before-hook возвращается и клиент продолжает обычное удаление. Плагин не вызывает `param.setResult` и не заменяет исходное удаление своим запросом.

Это до двух дополнительных запросов редактирования на сообщение. Успех запросов не проверяется: `sendRequest(req, None)` не получает callback, а `time.sleep` не является подтверждением приёма сервером или применения правки устройством получателя. Ошибки большинства операций подавляются.

| Исходный текст уже сохранён в независимой истории, уведомлении, пересланной копии или снимке экрана | В этом плагине нет механизма удаления такой копии. |
| Клиент сохраняет только текущую версию и успел принять правку | Возможна подмена отображаемого сохранённого текста; зависит от клиента и доставки. |
| Редактирование отклонено Telegram | Штатное удаление всё равно продолжится; плагин не проверяет отказ. |
| Правка прошла, а удаление не завершилось | У собеседника может остаться случайный текст либо грубая фраза от имени отправителя. |
| Удаляется медиа | Запросы меняют поле `message`, не заменяют сам файл. Попытка вставить 3900 символов в подпись может быть отклонена по ограничениям API. |

Называть случайный текст «стиранием памяти», «шифрованием» или доказанным обходом сохранения правок нельзя. В коде нет такой реализации.

### Полезные приёмы разработки

| Приём | Что показывает пример | Что нужно улучшить при переносе |
| --- | --- | --- |

### Недостатки, влияющие на работу

1. **Отсутствует проверка результата правки.** Telegram документирует, в частности, `MESSAGE_AUTHOR_REQUIRED`, `MESSAGE_EDIT_TIME_EXPIRED`, ошибки peer, слишком длинной подписи и entities. Плагин всё равно продолжает удаление.
2. **Не проверяется «удалить только у себя».** Хук не читает параметр удаления у всех. Поэтому подходящий вызов локального удаления тоже может инициировать видимое собеседнику редактирование сообщения.
3. **Не проверяется авторство и тип сообщения.** На попытку удаления чужого сообщения тоже могут быть отправлены неразрешённые запросы редактирования; для вложений нет отдельного безопасного пути.
4. **Определение типа диалога по числовым диапазонам ненадёжно.** `parse_dialog_id` использует несколько эвристик для отрицательных ID. `_protect_messages` сразу пропускает типы, которые эта функция назвала `channel`, `maybe_channel` или `secret`. Это ограничение и допущения реализации, не доказательство корректного распознавания всех диалогов Telegram. Проверки реального типа peer на этом этапе нет.
5. **Берётся выбранный аккаунт.** Вместо аккаунта перехваченного `MessagesController` используются `UserConfig.selectedAccount` и новый `getInstance`. При нескольких аккаунтах возможен неверный контекст.
6. **Паузы блокируют поток вызова.** В фоне код не запускается, несмотря на импорты `threading`, `run_on_queue`, `run_on_ui_thread`. Номинальные паузы составляют около `0.1 × N + 0.1` секунды на вызов с N сообщениями, плюс генерация текста и другие операции. Если вызов пришёл с UI-потока, интерфейс на это время будет ждать.
7. **Хукаются все перегрузки, аргументы считаются одинаковыми.** Защита проверяет только длину args, наличие `size()` и ненулевой `args[3]`; этого недостаточно для подтверждения подходящей сигнатуры.
8. **Снятие хуков требует сверки SDK.** Результат `hook_all_methods` добавляется в `_hooks` одним элементом, затем целиком передаётся в `unhook_method`. Если SDK возвращает коллекцию handle, её нужно разбирать; исключение здесь будет подавлено.

- [Telegram — messages.editMessage](https://core.telegram.org/method/messages.editMessage): параметры, флаги, ошибки и условия серверного редактирования.

Для разработки полезны перехват операции удаления, работа с Java-списками и создание TL-entities. Главное ограничение модели угроз: возможность изменить своё сообщение на сервере не даёт контроля над ранее сохранёнными копиями у получателя. ### Самое полезное для интерфейса: штатная точка входа

В `register()` вызывается:

```python
self.drawer_menu_id = self.add_menu_item(
    MenuItemData(
        menu_type=MenuItemType.DRAWER_MENU,
        text="Cashier",
        icon="msg_fave",
        on_click=self.open_from_context,
        item_id="cashier_dashboard",
        priority=60,
    )
)
```

`DRAWER_MENU` — главное боковое меню клиента, где также находится вход в настройки. При нажатии открывается отдельная панель статистики Cashier. Параметры самого плагина описаны отдельно через `create_settings()`. Никакого хука конкретной строки стандартных настроек здесь нет; используется готовый API SDK, без ZwyLib.

`text` задаёт подпись, `icon` — имя drawable клиента, `on_click` — обработчик, `item_id` — стабильный идентификатор, `priority` — относительный порядок среди пунктов. Это не обещание определённого места непосредственно рядом с конкретной строкой: расположение определяет реализация меню клиента. Актуальная документация SDK также описывает автоматическое удаление зарегистрированных пунктов при выгрузке плагина.

### Как открывается полноценный экран

1. `open_from_context` получает `fragment` из словаря контекста меню либо через `get_last_fragment()`.
2. Создаёт `_DashboardSession`, Python-делегат `_DashboardDelegate` и Java `UniversalFragment` из пакета `com.exteragram.messenger.plugins.ui.components.templates`.
3. Вызывает `parent_fragment.presentFragment(session.java)`, включая новый экран в штатную навигацию клиента.
4. Через `UniversalFragmentDelegate.afterCreateView` возвращает собственную иерархию Android View: `FrameLayout` → `ScrollView` → вертикальный `LinearLayout`.
5. Настраивает `ActionBar`: заголовок, кнопку назад, подзаголовок состояния и кнопку обновления.
6. Сохраняет ссылки на Java-фрагмент, Python-делегат, контейнеры и popup в объекте сессии. При уничтожении экрана закрывает popup, очищает ссылки и помечает сессию как уничтоженную.

При повторном открытии старый экран закрывается, период сбрасывается на текущий месяц, затем принудительно запускается синхронизация. Длительная работа не должна обновлять закрытый экран: `refresh_dashboard` проверяет `_alive`, текущую сессию и `destroyed` до постановки задачи и непосредственно на UI-потоке.

### Откуда берутся данные

**История Telegram.** Через `StarsController.getInstance(account)` читаются `transactions[0]`, баланс и состояние загрузки. `invalidateTransactions(True)` запускает перезагрузку, `loadTransactions(0)` — следующие страницы. `NotificationCenter.starTransactionsLoaded` сообщает о поступлении данных; `starBalanceUpdated` обновляет баланс. Таким способом можно получить доступные операции, совершённые до установки плагина, а не только перехваченные во время его работы.

**Предварительные записи.** `pre_request_hook` наблюдает `TL_messages_sendPaidReaction` и `TL_payments_sendStarsForm`, `on_send_message_hook` — `params.payStars`. `post_request_hook` для `TL_payments_getPaymentForm` сохраняет сумму формы в валюте XTR по `form_id`, суммируя `invoice.prices`. Кэш ограничен 64 формами. Хуки возвращают обычный `HookResult`, не блокируют и не изменяют запросы.

Live-расходы складываются в одну предварительную запись на категорию и местный день, помеченную `pending=True`. Для сверки используется история, где записи объединяются по ID. Сопоставление live и history существенно упрощено, что вызывает описанные ниже искажения.

Фоновая синхронизация после события откладывается на 8 секунд с перезапуском таймера при новых событиях. Завершение — когда контроллер загрузил всё, произошло 4000 событий загрузки, возникла ошибка следующей страницы либо сработал таймер 240 секунд. «4000» — предел событий, не число транзакций. При частичном результате отдельная отметка неполноты не сохраняется; интерфейс может показать обычное «Готово».

### Учёт аккаунтов, хранение и жизненный цикл

Данные пишутся в `cashier_data/account_<номер>.json` внутри каталога плагинов. Хранятся до 6000 записей операций и до 600 наблюдений баланса. Графика истории баланса нет: на экране показан текущий баланс, а графики относятся к расходам.

Используются `threading.RLock`, сохранение с задержкой две секунды, `run_on_queue` для загрузки/разбора, UI-поток для работы с View. Есть подписка на глобальное `NotificationCenter.activeAccountChanged`: плагин меняет контроллер, переподписывается на события, закрывает старый экран и загружает файл другого аккаунта. На выгрузке отменяет таймеры, закрывает экран, снимает observer и сохраняет данные.

Это полезная структура для многопользовательского Analytics, но изоляцию и сохранение нельзя считать безошибочными: ниже зафиксированы общие mutable-списки и потеря отложенного сохранения при смене аккаунта.

### Подтверждённые оговорки и ошибки

1. **Общие списки между «пустыми» хранилищами.** `dict(_EMPTY_STORE)` копирует словарь поверхностно; вложенные `transactions` и `balance_history` остаются общими. Изолированная проверка показала: добавление записи в одно свежее хранилище видно во втором. Это может переносить данные между свежими состояниями аккаунтов и мешать полной очистке. Нужны новые списки или глубокая копия, а не копирование внешнего словаря.
2. **Предварительная операция считается расходом до подтверждения.** Live-запись создаётся до ответа сервера; результата платёжного запроса код не проверяет. Если попытка не завершилась покупкой, запись может остаться. Агрегация нескольких live-расходов в один дневной bucket также искажает число операций и «крупнейшую трату» до сверки.
3. **Сопоставление live/history слишком грубое.** `history_confirms_day` удаляет весь live-bucket, когда найдена хоть одна отрицательная историческая операция той же категории в тот же день — сумма и соответствие конкретному платежу не проверяются. В тесте live −100 исчез после добавления отдельной исторической операции −1.
4. **Дробные звёзды теряются.** `extract_transaction` и баланс читают только `amount.amount`, игнорируя `nanos`. Синтетическая операция +0,5 Stars вернула `None`, так как целая часть равна нулю. Telegram документирует дробную часть отдельно.
5. **Не исключаются неуспешные и ожидающие записи.** Флаг `failed` читается во временный словарь, но не сохраняется в результирующей записи и не используется при подсчёте. `pending` отображается, но тоже входит в итог. В изолированной проверке записи failed −50 и pending −20 дали расходы 70. Возвраты учитываются по знаку как поступления; это валовые расходы, не обязательно чистая сумма после возврата.
6. **«Всё время» ограничено локально сохранёнными данными.** Отбрасываются записи после 6000 самых новых; частичная синхронизация может считаться завершённой. На экране доступны только 30 строк периода, без раскрытия остальных.
7. **Ошибка получения координат.** В `trigger_ripple` и `show_period_tooltip` вызван `view.getLocationOnScreen()` без аргументов. В стандартном Android View требуется `getLocationOnScreen(int[] outLocation)`. Без дополнительной адаптации моста этот вызов завершится ошибкой, поэтому экранная волна и popup могут не работать; обычный selector и изменение столбца выполняются отдельно. Для переноса нужно передать Java-массив из двух int и прочитать его после вызова.
8. **Смена аккаунта сбрасывает состояние до сохранения.** `switch_account` отменяет отложенное сохранение и заменяет `_store`, не вызывая сначала `store_save` старого аккаунта. Последние несохранённые изменения могут потеряться. В `merge_from_snapshot` аккаунт проверяется до разбора, но повторной проверки перед записью после разбора нет — возможен конфликт с одновременной сменой аккаунта.
9. **Очистка может выполниться без показанного подтверждения.** При отсутствии fragment или исключении в создании диалога `confirm_clear` сразу вызывает `clear_data`. Идущая синхронизация при очистке не отменяется и способна снова добавить операции.
10. **Часть описаний настроек шире реализации.** Обработчик `starBalanceUpdated` сохраняет баланс и обновляет экран, но сам не вызывает `request_sync`, хотя подпись обещает подгрузку истории при изменении баланса. Выключение «Показывать доходы» убирает строку суммы в карточке, не скрывает положительные операции из списка и счётчика. `on_setting_changed` пуст, поэтому немедленного обновления уже открытой панели по нему нет.
11. **Полная перестройка экрана и несовпадающие цвета.** Каждый `refresh_dashboard` удаляет все View и строит их заново с анимациями. Цвета диаграммы зависят от места категории в рейтинге, а цвета строк истории — от фиксированного `CATEGORY_ORDER`; одна категория может выглядеть разными цветами.
12. **Совместимость класса нужна уже при импорте.** `jclass(UniversalFragment...)` и импорт StarsController находятся на верхнем уровне, без резервного пути. Отсутствие классов в сборке остановит загрузку; в метаданных нет минимального SDK, который объяснил бы требование заранее.

### Как устроен нативный рендер

1. Плагин получает живые `MessageObject`, сортирует выделение по ID и ограничивает число сообщений. Соседние сообщения одного отправителя с интервалом менее 300 секунд группирует по верхнему/нижнему краю пузыря. Исходные позиции пропущенных сообщений в диалоге не учитываются.
2. `_preload_msgs` через `FileLoader` запрашивает фото/превью, видео, GIF, кружки, стикеры и анимированные стикеры, если нужного файла нет локально. Для запущенных загрузок проверяет готовность максимум шесть секунд. Это ожидание файлов, а не гарантия декодирования каждого `ImageReceiver`.
3. `_wallpaper` пытается нарисовать `backgroundView` текущего чата в bitmap, затем использует запасные способы получить Drawable обоев. `_render_bg` держит копируемый кеш по ID чата и размерам экрана до четырёх секунд.
4. Через `run_on_ui_thread` создаётся `ChatMessageCell(context, account, True, sharedResources, themeDelegate)`; ей назначается delegate, вызываются `onAttachedToWindow`, `setParentViewSize`, `setMessageObject`, `measure`, `layout`, затем `draw(canvas)`. Устанавливаются `drawingToBitmap = True` и, если доступно, `setFullyDraw(True)`.
5. Для служебных сообщений используется `ChatActionCell`. Альбомы собираются через `MessageObject.GroupedMessages`, `calculate()` и `posArray`; геометрия пересчитывается по долям ширины 1000. Подписи, имена, время, комментарии и реакции альбома частично дорисовываются специальными методами ячейки.
6. Отдельно настраиваются `ImageReceiver`, вызывается `ImageLoader.loadImageForImageReceiver`, дорисовываются аватары. Координаты имён и упоминаний извлекаются из внутренних layout-полей, после чего соответствующие области bitmap маскируются.
7. Изображения ячеек и альбомов обрезаются по вычисленным границам и склеиваются с промежутком 2 dp. Добавляются общий фон и поля, масштабирование, водяной знак и скругление; результат кодируется в PNG/JPEG. JPEG предварительно сводит прозрачность на белый фон.
8. Для стикера выполняется отдельный рендер. Прозрачные края обрезаются, изображение вписывается в предел 512×512, при обрезке добавляется отступ 8 px. Сначала пробуется WebP lossless, затем качества 100/92/84/74/64/54, пока размер не станет не больше 512 КиБ. При неудаче выдаётся ошибка, дальнейшего уменьшения разрешения нет.

Ключевой переносимый приём: можно использовать штатный View клиента как движок рисования, передавая ему свои входные объекты и контекст темы. Для обычных Android View сам подход `Canvas(Bitmap)` + `View.draw()` документирован. Но нужно корректно выполнить measure/layout, предоставить зависимости и учитывать особенности software-rendering.

«Пиксельная точность» здесь означает использование штатного рисовальщика, а не тождество скриншоту: ячейки создаются заново, сообщения перегруппировываются, фон масштабируется и обрезается отдельно, аватары частично позиционируются вручную. Масштаб 2× реализован через `createScaledBitmap` уже готового изображения, поэтому сам по себе не повышает исходную детализацию текста и фотографий. GIF, кружки и анимированные стикеры превращаются в статичное изображение/кадр.

### Дополнительное поведение: фонарик и вибрация при первом запуске

`on_plugin_load` проверяет `_first_run_done`; если это первый запуск, вызывает `_blink_flash()` и сразу сохраняет этот флаг. В фоновой очереди плагин пытается дать вибрацию 1300 мс с амплитудой 255, затем пять раз включить/выключить фонарик с паузами 100 мс. Настройки `load_vib` и `load_flash` по умолчанию True, но соответствующих строк в `create_settings` нет. При ошибке действие тихо пропускается, а отметка первого запуска уже сохраняется. Для переноса в другой плагин этот эффект следует делать явной настраиваемой функцией, а не забирать вместе с кодом интерфейса незаметно.

### Ограничения и подтверждённые детали, которые не стоит копировать вслепую

1. **Смещение маски после символов вне BMP.** `_username_bounds` ищет регулярным выражением в Python `str`, а найденные индексы передаёт Android layout без перевода в UTF-16. У Java индексы считают 16-битные единицы; часть эмодзи занимает две. На извлечённом методе с искусственным layout по 10 px на единицу строка `hi @alice_test` дала правильные границы `(29, -1, 141, 21)`, а `😀😀😀 @alice_test` — `(39, -1, 151, 21)` вместо `(69, -1, 181, 21)`. Это воспроизводит ошибку координат, но не является снимком реального Android-рендера. Исправление для будущей реализации — переводить смещения кода Python в UTF-16 перед обращением к Java layout.
2. **Анонимизация неполная.** Поиск `@username` охватывает `messageText`/`textLayoutBlocks`, без отдельного прохода по `captionLayout`, тексту ответа или служебному тексту. `_render_action` получает только флаг скрытия аватара, поэтому имена внутри служебных сообщений этой веткой не скрываются. Методы `_name_status`, `_name_verify`, `_get_admin_bounds`, `_sign_bounds` определены, но не вызываются; отдельного гарантированного скрытия подписей, ролей и связанных значков нет. Кроме того, включённый watermark с `{chat}` может снова поместить название чата на изображение.
3. **Изменение состояния спойлеров для картинки.** В ветке `hasMediaSpoilers() and not needDrawBluredPreview()` плагин временно выставляет флаги раскрытия медиа-спойлера в True. После ячейки он восстанавливает значения, но изображение к этому моменту уже нарисовано. Поэтому видимость медиа под спойлером в цитате может отличаться от исходного экрана. Флаги реакции, типа и подставного имени тоже временно меняют живой MessageObject с последующим восстановлением.
4. **Одна мутация не восстанавливается.** `msg.messageOwner.pinned = delegate.isPinnedMessage(msg)` записывается для живого объекта без сохранения старого значения. Delegate считает закреплённым только один ID из `getPinnedMessageId`. Это возможное локальное побочное изменение, а не отправка закрепления на сервер.
5. **Готовность медиа ограничена ожиданием.** Прелоад ждёт не больше шести секунд, после чего рисование продолжается. Отдельного ожидания полного декодирования аватаров и всех `ImageReceiver` перед `draw` нет. На холодном кеше результат может содержать заглушки или превью; фактический вид надо проверять на устройстве.
6. **30 сообщений не ограничивают число пикселей.** Большая часть работы View, альбомов и масок выполняется в одном UI-задании. Одновременно могут существовать bitmap ячеек, альбома, общего полотна, масштабированной копии и предпросмотра. Длинные сообщения и 2× могут заметно нагружать память и временно задерживать интерфейс. Фоновое ожидание ограничено `6 + 0.7 × количество сообщений` секундами; истечение этого срока не отменяет уже запущенное UI-задание. Аналогично ожидание обоев 2 секунды не отменяет отложенное рисование.
7. **«Отправлено» означает передачу в клиентскую очередь.** Успешная плашка показывается сразу после вызова prepare/send, без подтверждения доставки Telegram. При отправке как фото клиент может дополнительно изменить размер/качество; отправка как документ сохраняет подготовленный файл.
8. **Аккаунт не закреплён для всего конвейера.** Renderer читает `currentAccount` исходного чата, но загрузка/отправка используют текущие `selectedAccount`/`get_account_instance()`. При смене аккаунта между созданием цитаты и отложенной отправкой возможен неверный контекст. В новой реализации нужно передавать исходный account явно через весь процесс.
9. **Часть водяного знака работает не так, как можно ожидать.** `@username` — буквальный текст, не автоматическая подстановка своего никнейма. Пустая строка снова заменяется на `@username`, поэтому режим «только логотип» через пустой текст не достигается. Это подтверждено отдельным исполнением `_watermark_text_resolved`. `{count}` получает число итоговых элементов сборки; целый альбом считается одним элементом, поэтому число может отличаться от числа выбранных сообщений. В режиме плитки угол 0 заменяется на −30° через `angle or -30`.
10. **Пределы и кэш имеют особые случаи.** Масштаб отключается для sticker и явного аргумента `transparent=True`; выбранный в настройках прозрачный фон обычного PNG идёт другим путём и масштабируется. Предупреждение «для стикера будет сжато» основано на размере текущего PNG/JPEG, хотя стикер потом рендерится и сжимается отдельно. PNG в подписи назван «без сжатия», но формат использует сжатие без потерь.
11. **Совместимость зависит от внутренних деталей.** Часть вызовов имеет запасные сигнатуры, однако обязательные хук `addToSelectedMessages`, хук `hideActionMode` и класс delegate могут остановить загрузку на другой сборке. Некоторые ресурсы (`msg_gallery_solar`, `input_video_pressed_solar`) используются напрямую без проверки наличия. `themeDelegate` и `sharedResources` считаются обязательными для рендера.
12. **Жизненный цикл обработан частично.** Закрытие предпросмотра освобождает его bitmap, обычный успешный рендер отсоединяет временные View, выгрузка убирает кнопку, пункт меню и кэш обоев. Но задачи очереди явно не отменяются, фабрики/preview-delegates/view-ссылки полностью не очищаются, а имена временных экспортных файлов основаны на целой секунде. Повторные действия в ту же секунду могут обратиться к одному пути. При ошибках и таймаутах нет общего `finally`, освобождающего все промежуточные bitmap и отсоединяющего все ячейки.

Дополнительно проверено: `_picked_dialog` принимает неитерируемую Java-подобную коллекцию с `size/get`, возвращая `(-100, 42)` для объекта с dialogId/topicId; Python-список `[-100]` даёт `(-100, 0)`, пустая коллекция — `(0, 0)`. Это полезный пример совместимого чтения результата native UI.

Временные изображения хранятся в каталоге `quotecreate` внешнего кэша приложения, с запасным переходом на внутренний кэш. При загрузке удаляются файлы старше суток, кроме выбранного логотипа. При выгрузке очищается каталог или всё, кроме логотипа. Сам логотип не отправляется никуда автоматически: он используется при локальном наложении на цитату.

Раз в секунду цикл проверяет актуальную Activity и открытый личный чат. Если питомец пока не создан, `_start` повторяется через 700 мс. При паузе основная View не обязательно удаляется: прекращаются тики; удаление выполняется при скрытии, смене окна или выгрузке.

В `_on_new_messages` Java-список читается через `size()/get(i)`, как в chaTools и AntiAyugramDelete. Но `on_updates_hook` использует прямой `for item in items`: полностью совместимый обход контейнеров в файле не унифицирован. Это та же область риска, что отмечена для Ai Clone, без доказательства сбоя в конкретном Java-мосте пользователя.

### Рисование персонажа, текстуры и кэш кадров

`_update_metrics` задаёт сетку **18×13** и ячейку 3/4/5 dp с переводом в пиксели. Приблизительные размеры до округления dp — 54×39, 72×52 или 90×65 dp. Готового спрайт-листа с растровыми позами в файле нет: `_render_frame` рисует прямоугольники `Canvas.drawRect` на `Bitmap.Config.ARGB_8888`.

Ключ кадра:

```python
(eyes, look, arms, legs, squash, blush)
```

Глаза, направление взгляда, руки, ноги, сжатие/растяжение и румянец выбираются отдельно. `_compose` строит ключ из текущего состояния, `_get_frame` возвращает bitmap, `_render` меняет картинку только при смене ключа. Движение уже готового кадра выполняется через `setTranslationX/Y` и `setRotation`, а не повторное рисование всей картинки на каждый сдвиг.

### Физика и распознавание жестов

У своего питомца состояния `idle`, `walk`, `sleep`, `press`, `drag`, `pet`, `fly`. Прыжок хранится независимо через `_hop_active`, `_hop_off`, `_hop_vy`; выражение глаз и срок его действия — отдельными полями. Такая декомпозиция позволяет, например, двигаться и временно улыбаться без создания отдельного состояния на каждую комбинацию.

`_step` берёт `time.monotonic`, рассчитывает `dt`, обновляет поведение и физику, затем кадр, гостя и облачко. `_step_ground` отвечает за ходьбу/сон/случайные действия; `_step_fly` — за свободное движение и столкновения; `_land` останавливает полёт и сохраняет положение.

Ускорение гравитации и прыжка — 2600 dp/с². Ходьба — 42 dp/с, возвращение гостя — 34 dp/с. С гравитацией горизонтальная скорость затухает через `exp(-0.35*dt)`, без неё обе компоненты — через `exp(-2*dt)`. Отражение от стен сохраняет 55% скорости; вертикальный отскок от пола с гравитацией — 42%. Это простая локальная модель, не Android physics engine.

| Жест | Распознавание | Обработчики и результат |
|---|---|---|
| Одиночный тап | Отложенное действие через 360 мс | `_tap` → `_schedule_ask` → `_fire_ask`; небольшой прыжок и диалог. |
| Двойной тап | Между отпусканиями менее 0,32 с | Отмена ожидающего диалога, прыжок с большей скоростью, искры. |
| Удержание | Состояние `press` ≥0,4 с | `_start_pet`; сердечки и тактильный отклик. |
| Поглаживание | Горизонтальные движения более 10 dp со сменой направления | `_stroke`; дополнительная частица. `pets_count` увеличивается один раз при завершении сеанса в `_end_pet`, не на каждый проход пальца. |
| Перенос | Сдвиг более 8 dp до перехода в поглаживание | `_on_touch` переводит в `drag`, координаты следуют за пальцем с сохранением смещения точки захвата. |
| Бросок | История последних примерно 0,1 с; последняя точка моложе 0,08 с | `_release_drag` оценивает скорость. При >700 dp/с либо включённой гравитации — `fly`; компоненты ограничены ±6000 dp/с. |
| Касание гостя | `_tg_remote_touch` | Тап запускает прыжок; перенос — `carried`; отпускание рядом со своим питомцем запускает готовый разговор. Во время `talk` жесты поглощаются. |

Устройство позиции: `_save_position` переводит координаты доступной области в целые 0–1000, `_restore_position` восстанавливает их под текущую геометрию. `_bounds` учитывает размеры окна и системные верхний/нижний отступы, кэширует результат на 0,4 с. Это не полноценная работа с IME: проверки `WindowInsets.Type.ime`, как в chaTools, здесь нет.

### Планирование анимации и защита от устаревших действий

`_schedule` сначала снимает прежний callback, затем ставит один новый через `Handler.postDelayed`. `_next_delay` выбирает 16 мс при активном действии своего питомца, 80 мс в покое, 250 мс во сне, 1000 мс при отсутствии View. Это адаптивный таймер; синхронизации с vsync/Choreographer в файле нет.

Три полезных применения счётчика поколения:

1. **Отложенный тап:** `_ask_token` увеличивается при планировании и отмене. Старый callback может остаться в очереди, но `_fire_ask` проверит токен и не откроет диалог. `_unloaded`, `_paused` и существование питомца проверяются отдельно.
2. **Результат ИИ:** `_ai_request_id` общий для вопроса и генерации плагина. Показывается/отправляется только результат последнего запроса; старый HTTP-запрос при этом продолжает выполняться до ответа/ошибки.
3. **Исчезновение облачка:** `_bubble_gen` позволяет старому `withEndAction` не скрыть новое облачко, появившееся во время прежней анимации.

Это конкретные примеры исправления класса ошибок отмены, встреченного в Ai Clone, и устаревшего превью из Quote. Проверка поколения решает доставку результата; она сама по себе не останавливает сетевую задачу, не освобождает её ресурсы и не сохраняет очередь после завершения процесса.

### Реакции на переписку: нормализация, приоритеты и дедупликация

`_port_text` получает текст из SDK hooks или MessageObject. `_extract_update_text` ищет текст в `message`, `messageOwner.message` либо `text`; направление берётся из `out` или `isOutOwner`.

Нормализация — `strip`, нижний регистр и `ё → е`. Свои слова любви, грубости и исключения задаются через запятую. Проверка — обычное `word in text`; после исключений приоритет **любовь → грубость → смех**. Любовь и смех дают happy, грубость — angry. Входящая любовь добавляет сердечко в облачко, входящая грубость — одну из встроенных реплик о собеседнике. Подпись настройки про «испуг» шире реального поведения: в коде для грубости angry.

Набор текста вызывает surprised на 0,7 с и случайное направление взгляда, если сейчас не действует happy/angry. Проверки соответствия текущему чату и конкретного типа typing action нет. Прочтение сообщений и отправка собственного typing в этой функции не выполняются.

Дедупликация использует `(полный текст, outgoing)` за 1,5 с. Это попытка убрать повтор одного события из нескольких каналов, но ключ не содержит ни аккаунта, ни диалога, ни message_id. В отличие от желаемой схемы из chaTools, разные сообщения здесь могут ошибочно сливаться. Подписки и hooks также не фильтруют обычные реакции по открытому чату: питомец способен реагировать на события другого диалога/аккаунта.

### Together: версионированный снимок вместо живой синхронизации

Ключевые методы: `_tg_invite_command`, `_tg_sync_text`, `_tg_on_sync`, `_tg_prompt_invite`, `_tg_accept`, `_tg_apply_sync`, `_tg_join`, `_together_step`.

1. Пользователь выбирает Together или пишет `.clawdinvite`. Исходящий hook отменяет отправку самой команды и вызывает отправку одного обычного JSON-сообщения.
2. `_tg_sync_text` добавляет `type="clawd_sync"`, `version=1`, `x/y`, `gravityMode`, `screenW/H`, `petW/H`, `color`, `eyeColor`; необязательно `texture` и `textureSize`.
3. `_tg_texture_b64` уменьшает локальное изображение до 32/24/16/12/8 px по длинной стороне, сохраняет PNG через `ByteArrayOutputStream` и пытается уместить base64 в 2600 символов.
4. `_tg_on_sync` принимает только входящий JSON версии 1 в положительном dialog_id при включённом Together. Ранее принятые пары и глобальный auto-accept обходят повторный вопрос; иначе появляется диалог согласия.
5. `_tg_accept` сохраняет согласие и снимок, пытается показать питомца и затем удалить приглашение **у обеих сторон**. Отказ оставляет сообщение. Полная проверка снимка перед сохранением не проводится.
6. `_tg_apply_sync` переводит позицию отправителя в доли его экрана за вычетом размеров питомца. На стороне получателя доли переносятся в локальные границы. Размер гостевого ImageView берётся из локальной настройки, а не из `petW/H` отправителя.
7. При входе в соответствующий чат `_tg_join` загружает сохранённого гостя. Затем `_tg_step_remote` самостоятельно рассчитывает его ходьбу, полёт, прыжки, мигание, перенос, разговор и возвращение домой.

Снимки хранятся в `together_syncs` по ключу `account:dialog`, принятые приглашения — в `together_accepted`, дружба — в `together_friends`. Это один из примеров, где автор действительно включает аккаунт в ключ состояния. Для двустороннего показа оба участника должны отправить свой снимок.

**Непрерывного обмена событиями нет:** `_together_event` немедленно возвращается. Перенос, прыжок, эмоция и движение одного телефона не транслируются на другой. Полученный образ может оставаться доступным, когда плагин собеседника уже не работает; актуальное присутствие протокол не подтверждает. Новые настройки и позиция сами по себе не отправляются — нужен следующий снимок.

При переносе гостя к своему питомцу `_tg_start_talk` запускает `_tg_build_script`: готовые фразы зависят от гравитации обоих и факта дружбы. `_tg_step_talk` проигрывает их по времени. При первой дружбе `_tg_befriend` **автоматически отправляет в настоящий чат** отдельную строку «Клавдики теперь друзья»; код её не удаляет. Раз в пять секунд проверяется наличие этой строки среди максимум 150 уже загруженных сообщений открытого чата, с запасным доступом к private `messages` через reflection. Обычная случайная встреча через `_tg_check_meeting` даёт эмоцию и сердце, но не запускает весь разговор.

Комментарии «ничего не удаляем и не отвечаем автоматически» устарели. Фактически JSON удаляется после принятия, а фраза дружбы отправляется автоматически и остаётся. Это пример, где описание протокола надо выводить из активных путей вызовов, а не из соседнего комментария.

### Отправка, удаление и форматирование через внутренние контроллеры

| Задача | Реализация и граница вывода |
|---|---|
| Отправить JSON/фразу | `_tg_send`: `SendMessagesHelper.SendMessageParams.of(text, dialog)`, `params.notify=False`, `getInstance(account).sendMessage(params)`. Успех означает вызов метода, не подтверждённую сервером доставку. |
| Запасная отправка | `client_utils.send_message({"peer": dialog, "message": text})`. В этой ветке теряются явный аккаунт и тихий режим. |
| Удалить приглашение | `_tg_delete` строит Java `ArrayList<Integer>` через `jint`/`Integer.valueOf`, затем пробует четыре перегрузки `MessagesController.deleteMessages`. Фактическое удаление на сервере отдельно не подтверждается. |
| Кодовые блоки | `_tg_send_code_block` создаёт Java `CharSequence[]`, вызывает `MediaDataController.getEntities(arr, True)`, берёт изменённый `arr[0]`, задаёт `params.entities` и отправляет через аккаунтный SendMessagesHelper. |
| Длинный ответ | `_send_code` собирает блоки около 3800 Python-символов по границам строк, добавляя тройные обратные кавычки. Одну слишком длинную строку не дробит; UTF-16-длину отдельно не рассчитывает. |

В сравнении с AntiAyugramDelete здесь не создаётся TL-запрос редактирования: приглашение удаляется через штатный контроллер. Общая граница остаётся прежней: отсутствие исключения Java-вызова не равно серверному подтверждению операции. Перебор перегрузок тоже не доказывает совместимость со всеми сборками.

### ИИ: три протокола, последний результат и генерация исходника

Основные методы: `_ai_setup`, `_ask_ai`, `_ai_worker`, `_call_gemini`, `_call_claude`, `_call_openai_compatible`. Для генерации — `_ask_plugin`, `_plugin_worker`, `_clean_plugin_code`, `_send_code`.

| Адаптер | Запрос и чтение ответа |
|---|---|
| Gemini | POST `https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent`, заголовок `x-goog-api-key`, `contents` и `generationConfig.maxOutputTokens`; читает текст первого кандидата, пропуская части с `thought`. |
| Claude | POST `https://api.anthropic.com/v1/messages`, `x-api-key`, `anthropic-version: 2023-06-01`, отдельный `system`, `messages`, `max_tokens`; объединяет блоки `type="text"`. |
| OpenAI-совместимый | К base URL добавляется `/chat/completions`; необязательный Bearer, `model`, system/user в `messages`, `max_tokens`; читает `choices[0].message.content`. |

Третий адаптер используется для OpenAI, DeepSeek, Qwen и своего адреса. Пользовательский URL и модель обязательны, ключ для custom может быть пустым. Это реализация контрактов в данном файле, не гарантия совместимости любой текущей модели. Значения по умолчанию: `gemini-flash-latest`, `claude-haiku-4-5-20251001`, `gpt-4o-mini`, `deepseek-chat`, `qwen-plus`. Пример `claude-haiku-5.5` из сопровождающего сообщения не совпадает с default исходника; доступность моделей и стоимость не проверялись.

В отличие от Ai Clone, обычный вопрос здесь не включает историю Telegram или предыдущие вопросы. Передаются фиксированная инструкция питомца и текущий введённый текст. Gemini получает их склеенными в `contents`; Claude и совместимые серверы — системной инструкцией и пользовательским сообщением. Локальные реакции на чат не отправляют его историю в ИИ.

HTTP работает в `threading.Thread(..., daemon=True)`, результат возвращается через `run_on_ui_thread`; вывод ограничен последним `_ai_request_id`. Обычный `requests.post(timeout=30)` получает лимит 1024 токена для Gemini, 300 для остальных. Потоковой выдачи и истории диалога нет. Timeout requests не следует считать отдельным гарантированным общим дедлайном всей задачи.

`PLUGIN:` распознаётся **в диалоге вопроса питомцу**, в том числе при режиме `phrase`. Генератор использует отдельный промпт SDK, 8000 токенов и timeout 150 с. Аккаунт и чат фиксируются при запуске запроса; если пользователь позже откроет другой чат, результат всё равно уходит в первоначальный. Предпросмотра перед отправкой в этой реализации нет. Результат — сообщения с исходным кодом, не файл `.plugin`; установки и исполнения сгенерированного кода нет.

`_clean_plugin_code` лишь ищет `__id__` и `BasePlugin`, отрезает вступление и хвостовое Markdown-ограждение. Наличие двух слов не является проверкой AST, корректности SDK или результата на телефоне. Текст `PLUGIN_SYSTEM_PROMPT` — инструкция модели, а не перечень дополнительных вызовов, выполняемых самим Clawd. В исполняемом коде плагина нет `eval/exec` для запуска ответа модели.

### Подтверждённые проверки и недостатки

| Наблюдение | Результат изолированной проверки или вывод по активному коду |
|---|---|
| Нулевой индекс текстуры теряется при перечитывании | `_reload_cfg`, строка 1852: `int(g("texture_size", 3) or 3)`. Числовой 0 превращается в 3: 2 dp становятся 6 dp. Это повтор известной ошибки `or default` из iOS Circle и Quote. |
| Реакция срабатывает внутри слова | `_port_text("плохой")` даёт angry, потому что проверяется подстрока «лох». Нужны осмысленные правила границ/нормализации, а не копирование этого списка без проверки. |
| Категории конкурируют по фиксированному приоритету | «спасибо, идиот» даёт happy: ветка любви находится раньше грубости. Это подтверждённый порядок, не понимание смысла фразы. |
| Разные сообщения сливаются как дубли | Два вызова с «люблю» в 1,5 с дают одну реакцию. Идентификаторы чата/аккаунта/сообщения не входят в ключ. |
| Набор текста не привязан к открытому собеседнику | Вызов `_handle_port_update("TL_updateUserTyping", пустой объект)` уже даёт surprised. Для эффекта в конкретном чате нужны account/dialog/user и проверка текущего экрана. |
| Гость и танец не управляют частотой тиков | `_next_delay` учитывает только своё состояние. Отдельно подтверждены 80 мс для idle и 250 мс для sleep; активность гостя/разговор не добавляют 16 мс. Плавность на устройстве не измерялась. |
| Время физики отстаёт от таймера | `_step` ограничивает `dt` значением 0,05 с; проверка 0,08 → 0,05 подтверждена. При идеальных тиках 80 мс симуляция учитывает 62,5% времени, при 250 мс — 20%. Это особенно влияет на гостя, пока свой питомец спокоен/спит. |
| Выбор «Никогда» не будит уже спящего | `_on_cfg_change("sleep", 3)` меняет таймер, но оставляет состояние `sleep`; подтверждено. В ветке сна возврат происходит до проверки нового timeout. |
| Реплики зависят от разрешения гулять | При `wander=False` `_step_ground` возвращается раньше случайного `_say("idle")`; подтверждено. Реактивные реплики и явный ввод могут работать отдельно. |
| Заданный интервал не является точным расписанием | `_say("idle")` только запрещает слишком раннюю реплику; сама попытка выбирается случайной веткой поведения. После 57 с или случайных 20–40 с фактическая пауза может быть дольше. |
| Длинная одиночная строка не режется | `_send_code` со строкой из 5000 символов создал один блок длиной 5008 с ограждением. Задуманное ограничение 3800 не соблюдается на этом вводе. |
| Фильтр генератора принимает сломанный синтаксис | `_clean_plugin_code("__id__ = ; BasePlugin")` возвращает текст. Код не исполняется, но может быть отправлен пользователю как будто готовый плагин. |

Всего выполнено 12 проверок: idle/sleep-задержки и ограничение dt считались отдельными проверками, часть строк таблицы — чисто статические наблюдения. Тесты подтверждают описанные результаты Python-логики, а не запуск плагина на Android.

Дополнительные ограничения для переноса:

1. **Недостаточная проверка Together до сохранения.** Проверяются JSON/type/version/x/y, но не конечность float, разумные размеры экрана и изображения, диапазоны цвета и лимит декодированных пикселей. Согласие и снимок сохраняются до полного применения. Штатный отправитель ограничивает base64, принимающая сторона не повторяет этот лимит.
2. **Потеря account в резервных ветках.** Основные вызовы Java используют явный account, а оба запасных `send_message` — нет. Это продолжение проблемы из Ai Clone, AntiAyugramDelete и Quote. Нужна область аккаунта во всём конвейере; способ передачи зависит от установленного SDK.
3. **Текстура может задерживать UI.** `decodeFile`, масштабирование, PNG-сжатие и создание кадров находятся в UI-цепочке. Размер исходного файла/число пикселей заранее не ограничены. Нагрузка и память на телефоне не измерялись; сам факт отсутствия `Bitmap.recycle` в этом коде ещё не доказывает утечку.
4. **Облачко не защищено от других источников текста.** «Думаю…» и ИИ-ответ могут быть заменены реакцией чата, случайной репликой или Together. Request id защищает от старых ИИ-ответов, но не задаёт приоритет между разными подсистемами облачка.
5. **Закрытие приглашения системным способом.** `_tg_prompting` очищается кнопками «Принять»/«Нет», отдельного onDismiss для системной кнопки назад или закрытия жестом нет. Возможное повторное приглашение после такого закрытия требует проверки на устройстве.
6. **Хранение чувствительных параметров и совместимость.** Ключи передаются в обычные `Input` и `set_setting`; отдельного шифрования в файле нет, свойства хранилища определяет SDK. `requests` импортируется на верхнем уровне, `__requirements__` и минимальные версии не объявлены. Это основания проверить среду, а не утверждать несовместимость заранее.

### Выводы для следующих разработок

Главное новое — небольшой живой UI-объект внутри окна клиента: собственная генерация растровых поз, независимые признаки состояния, физика и жесты, повторяемые текстуры, локальный персонаж по полученному снимку и конкретные токены отмены устаревших действий.

При переносе анимационного цикла надо учитывать активность **обоих** персонажей, разговор, танец и эффекты. Ограничение большого dt после паузы допустимо как защита от скачка, но регулярный шаг 80/250 мс нельзя постоянно считать как 50 мс: нужен согласованный таймер либо учёт времени подшагами/аккумулятором. Это рекомендация для новой реализации, в исходнике такого исправления нет.

Для будущих плагинов можно применить эти приёмы к плавающему индикатору состояния, компактному таймеру, помощнику с локальными реакциями, интерактивной мини-сцене или совместному обмену оформлением. Для обмена данными заранее определить, что передаётся: снимок или живые события; отдельно задать версию схемы, согласие, обновление, удаление служебных сообщений и подтверждение операций. Локальная симуляция чужого персонажа не должна выдаваться за актуальное действие собеседника.

### Новое знание: непрочитанные — это сохранённый диапазон, а не одно число

Открытие Telegram-чата может быстро обнулить `unread_count` и продвинуть `read_inbox_max_id`. Если читать только текущий счётчик после нажатия кнопки, нужные сообщения уже могут считаться прочитанными.

Новая структура данных — неизменяемый `UnreadBounds(read_max, upper_id, count)`. Она хранит нижнюю границу прочтения, верхнее сообщение снимка и справочный счётчик. Запрос выбирает входящие сообщения с условием:

```python
read_max < message.id <= upper_id and not message.out
```

`_chat_state` индексирует экран отдельно и сохраняет идентичность `(account, dialog_id, thread_id)`. Снимок предпринимается после `onFragmentCreate` и до `createView`; если состояние уже изменилось, используется сохранившийся разделитель `first_unread_id` как граница первого непрочитанного. Наличие верхней границы защищает от включения новых сообщений, поступивших уже после сохранения снимка.

Для обычного чата источник — `MessagesController` исходного аккаунта и его dialog. Для темы — `TopicsController.findTopic` и состояние именно этой темы; в поддерживаемых ветках используются поля thread-состояния ChatActivity. Нельзя подставлять границу всего форума в неизвестную тему. Если достоверный интервал не найден, функция возвращает `None`.

Снимок относится к текущему экземпляру экрана и остаётся в памяти, пока тот жив. Возврат к прежнему экземпляру может сохранить его первоначальный диапазон. Это не постоянно обновляемое зеркало текущих статусов чтения и не восстановление исторических непрочитанных после перезапуска процесса.

### Пагинация: продвижение страницы отдельно от отбора текста

Ключевые методы — `fetch_unread_history`, `request_history_page`, прежний `build_transcript`.

1. `request_history_page` использует `TL_messages_getHistory` для обычного чата и `TL_messages_getReplies` с `msg_id=thread_id` для темы/ветки. Аккаунт фиксируется в `Job` и проходит через `send_request` и отмену.
2. `min_id` задаётся нижней границей чтения, `max_id` — `upper_id + 1`, потому что верхняя граница Telegram-запроса исключающая. Для предельного int-значения сохраняется локальный фильтр диапазона без переполнения.
3. Номер следующей страницы определяется минимальным допустимым ID всех полученных записей, включая свои сообщения и медиа без подписи. Их отсутствие в итоговом тексте не должно останавливать чтение более ранних страниц.
4. В результирующий набор попадают только входящие внутри зафиксированных границ; дубликаты устраняются по ID. Счётчик unread используется как подсказка, а не как условие ранней остановки.
5. Корневое сообщение темы, которое getReplies может вернуть как дополнительную запись, пропускается отдельно. Его старый ID не означает, что достигнута граница полезных ответов.
6. Остановка — пустая/короткая серверная страница, достижение нижней границы либо явная ошибка. Повторившийся offset, ошибка после частичной загрузки и превышение 30 страниц не выдаются за успешную полную сводку.
7. `build_transcript` сохраняет прежний порядок по времени, обработку текста/подписей/опросов, бюджет и сообщение о пропущенных старых текстах. Медиасодержимое без текста не распознаётся.

Это исправляет слабые места донорской схемы: там пустая отобранная пачка могла завершать чтение, offset продвигался по выбранным сообщениям, а при ошибке после нескольких страниц мог возвращаться частичный результат как обычный успех. Переносить стоит пользовательский приём и полезные поля, проверяя алгоритм, а не весь старый код без изменений.

### Перехват плашки и владение обработчиком

`SummaryChatHook` наследуется от `MethodHook`. Хуки жизненного цикла устанавливаются через `hook_all_methods`, а для `ChatUnreadCell` — через `hook_all_constructors`. Обрабатываются все найденные конструкторы, а не только первый.

`_wire_unread_cell` сначала проверяет, что найденная ячейка действительно находится внутри корня соответствующего чата. Она читает прежний listener и clickable/focusable, назначает свой `OnClickListener` и хранит слабую Java-ссылку на target. Локальная ссылка на Python proxy сохраняется, пока обработчик используется.

При detach прежний listener возвращается **только если текущий listener по-прежнему принадлежит этому плагину**. Если другой плагин успел поставить свой, его обработчик не перезаписывается. После восстановления возвращаются прежние clickable/focusable. Такой подход уменьшает конфликты, но не делает одновременный запуск двух обработчиков одной и той же плашки совместимым автоматически.

### Жизненный цикл и защита контекста

Хуки: после `onFragmentCreate`, до/после `createView`, после `onResume`, до `onPause`, до `onFragmentDestroy`; дополнительно события приложения PAUSE/RESUME. При паузе удаляются свой круг, OnPreDraw и обработчики ячеек. При возврате интерфейс прикрепляется заново. При уничтожении фрагмента состояние удаляется; при выгрузке плагина снимается каждый отдельный hook handle и очищаются UI-ссылки.

`_chat_is_current` проверяет актуальный fragment, account/dialog/thread и выбранный аккаунт. Даже ещё существующий View прежнего чата не должен запускать сводку в новом контексте. Отдельный `Job` получает неизменяемые настройки, исходный аккаунт, диалог, тему и snapshot границ. Существующая проверка аккаунта перед подтверждением AI-передачи сохранена.

Отдельно проверено, что повторное прикрепление создаёт один View и один observer, а PAUSE снимает оба. Все операции с интерфейсом выполняются в UI-путях/через `run_on_ui_thread`. Сетевой конвейер остаётся в фоне. Чтение/формирование сводки само по себе не вызывает нового `markDialogAsRead`: обычное поведение чтения при открытии чата определяет клиент Telegram.

Перед исправлением проверены импорты и параметры конструкторов меню/настроек по [официальным stubs SDK 1.4.3.8](https://github.com/exteraSquad/plugins-pysdk-builds/releases/tag/sdk-v1.4.3.8-stable-25018973248-1). Это опубликованные stubs **1.4.3.8**, а не точная копия SDK телефона 1.4.3.3; равенство сред и совместимость всех Java-классов по такой сверке не утверждаются. Фабрика декора без release и новые SDK account-хелперы в существующем коде уже защищены проверками возможностей/версии, а кнопка имеет ветвь старых полей ChatActivity.

Все 32 прошли. Подтверждено устранение данного ограничения метаданных; проверка установки и интерфейса на реальном телефоне по-прежнему нужна.

Актуальная исправленная сборка — `chat_summary_3.4.1.plugin`, SHA-256 `e5508591c0d5b051197eb2a5a8d151da18d0941f079bca26ff2ece8061630edb`. Версия 3.4.0 выше в разделе сохранена как история разработки и была отклонена установщиком на телефоне пользователя.

**Почему мог не работать выбор непрочитанных.** После открытия Telegram меняет read boundary и unread flags. Недостаточно читать счётчик в момент позднего нажатия или молча выходить, если границы отсутствуют. Добавлен before-hook `MessagesController.markDialogAsRead`: до штатного обновления сохраняются исходные account/dialog/thread и `UnreadBounds`. Дополнительно используется `unreadMessageObject` и его позиция в `ChatActivity.messages`, где более новые сообщения находятся перед разделителем. Неизменяемый snapshot передаётся в Job; пагинация не перечитывает уже обновлённую границу. Для темы не берётся read state общего родительского форума.

В выборе объёма пункт непрочитанных доступен всегда. При отсутствии snapshot нажатие повторяет попытку восстановления из текущего чата, затем показывает объяснение. Нажатие на разделитель в таком случае открывает обычный выбор последних сообщений. Неизвестные границы не подменяются полной историей. Восстановление по видимому разделителю ограничено локально доступными ID, поэтому предпочтителен ранний snapshot контроллера/first_unread_id.

У `ChatUnreadCell` могут отличаться корень и `backgroundLayout`, а исходный onTouch может поглотить click. Обрабатываются оба доступных target с проверкой принадлежности корню чата. `View.OnTouchListener` отслеживает DOWN/UP, отмену и сдвиг больше 8dp: короткое нажатие запускает один раз, перетаскивание не запускает сводку. При очистке восстанавливаются прежние click/touch listeners только если текущий обработчик всё ещё принадлежит плагину. Слабая Java-ссылка, сильная ссылка на proxy и прежние clickable/focusable сохраняются до detach. Совместное включение отдельного Unread Summary по-прежнему нежелательно из-за общего target.

**Ссылки на сообщения, из которых получен контекст.** В JSONL каждого реально отобранного сообщения добавлен `id`. `Transcript.sources` содержит только записи, прошедшие входной бюджет: `(id, time, excerpt)`. В локальном Transcript сохраняются account/dialog/thread и тип peer. Исходные имена остаются локальными при включённой анонимизации; ID сообщения сам по себе не делает ссылку публичной. Системная инструкция просит модель ссылаться на факты через `[id]`/`[id1, id2]` и запрещает выдумывать ID/URL.

`source_html` экранирует весь модельный текст и создаёт HTML-ссылки только для разрешённых ID. Произвольный HTML модели не исполняется; неизвестные числовые ссылки не превращаются в переходы. Для канала/супергруппы с Java MTProto dialog_id используется `https://t.me/c/<abs(dialog_id)>/<message_id>` и `?thread=<topic_id>` для темы. В этом API отрицательный ID канала не имеет Telethon-префикса `-100`, его нельзя механически удалять как строку. Личные/старые групповые чаты получают client-local `tg://openmessage?...`, это не публичные permalinks. Telegram требует доступ к исходному чату для открытия закрытой ссылки.

Результат рендерит разрешённые ссылки через `Html.fromHtml`/`LinkMovementMethod`. Отдельная кнопка «Источники» показывает сначала процитированные, затем остальные сообщения входного контекста, по 40 на страницу. Нативный переход создаёт `ChatActivity(Bundle)` с user_id/chat_id, message_id и topic_id, проверяет исходный выбранный аккаунт. Копирование/поделиться включают URL. Список обеспечивает доступ ко всему использованному контексту даже без ссылок в ответе AI. Проверка допустимого ID не подтверждает смысловую точность цитирования моделью.

### Chat Summary 3.6.0: весь непрочитанный диапазон, панель результата и повторный просмотр

Уточнение владельца после 3.5.0: полностью удалить выбор последних 50/100/200/500; брать весь сохранённый диапазон непрочитанных; использовать подачу результата первого варианта; распространить оформление на все собственные экраны; переставить кнопку сводки со штатным меню ⋮; две минуты после готовности коротким нажатием показывать результат, удержанием создавать новый. В ответе на уточнение владелец подтвердил, что под «кнопкой интерфейса» имел в виду **штатное меню ⋮**.

Изменения 3.6.0 заменяют описание выбора объёма, нижнего круга и карточек результата из предыдущих записей раздела. Прежние записи сохраняются как история, актуальный пользовательский путь описан ниже.

**Непрочитанные без выбора количества.** `_show_count_picker`, `MSG_COUNTS`, пресеты с count_index и публичный режим последних N удалены. Все входы создают Job только с `UnreadBounds`; отсутствие границ не подменяется общей историей. `_show_presets` теперь открывает только стиль/длину ответа. `fetch_history` делегирует загрузку непрочитанных, отсутствие bounds — явная ошибка. `fetch_unread_history` не ограничен прежними 30 страницами: остаются строго убывающий offset, нижняя граница snapshot, защита от повторной страницы, отмена, таймаут Telegram и проверка аккаунта/темы. Счётчик unread_count служит подсказкой, не числом записей, после которого надо остановиться.

Новая сводка в открытом чате сохраняет исходный нижний read_max и расширяет верхнюю границу по актуальному snapshot/последнему сообщению диалога, чтобы включить доставленные после открытия сообщения. Это сводка диапазона, сохранённого при открытии; Telegram по-прежнему может штатно отметить чат прочитанным. Для новой темы не берутся границы другого чата. Секретные чаты, специальные режимы и monoforum не подменяются обычной историей.

**Количество сообщений и бюджет API — разные ограничения.** Просто удалить выбор N недостаточно: прежний `build_transcript` оставлял только последние записи в пределах 24/48/96 тысяч символов. Для нового пути `complete_transcript` сначала строит полный хронологический JSONL с единым сопоставлением псевдонимов, затем `partition_records` разбивает его на части по бюджету символов/байтов. Длинная отдельная запись режется по тексту с тем же message_id и `continued=True`, без разрыва JSON и потери Unicode. Все исходные записи сохраняются в `Transcript.sources`; omitted/clipped в этом пути равны нулю. Медиа без текста/подписи и служебные записи по-прежнему не отправляются как выдуманные текстовые сообщения; OCR и распознавание голоса не добавлялись.

`summarize_complete` обрабатывает все части и рекурсивно объединяет все промежуточные сводки. Число групп должно уменьшаться; при невозможности поместить промежуточные результаты возвращается явная ошибка бюджета, а не результат с молча отброшенными старыми частями. Для промежуточных запросов длина ответа ограничивается относительно размера части, итоговый запрос сохраняет пользовательский максимум. ID внешних JSONL-записей при объединении — номера частей: инструкция отдельно запрещает использовать их как ID исходных сообщений. Токены агрегируются по запросам; достижение лимита генерации любой частью отмечается как возможная неполнота. Большой вход означает несколько API-запросов и возможные дополнительные расходы; экран существующего подтверждения передачи показывает количество частей и необходимость запросов объединения. После подтверждения выполняется весь согласованный конвейер, а не отдельное подтверждение каждой части.

`input_index` теперь задаёт **размер одной части**, а не число/общий лимит отправляемых сообщений. Ограничения реального контекста модели, API и сервера остаются: отсутствие произвольного лимита сообщений не означает бесконечный контекст модели. Источники подтверждают только допустимость ID/контекста, а не смысловую точность пересказа AI.

**Нижняя панель и ссылки.** За образец подачи взят `_show_summary_bottom_sheet` исходного Unread Summary: `BottomSheet`, отдельный заголовок, метки языка/сервиса, счётчик, прокручиваемое тело, действия и закрытие. Вместо прежних раскрывающихся карточек Chat Summary используется единое читаемое тело. Оригинальная функция использовала `parse_markdown`; в новой адаптации применён безопасный renderer `summary_markup` через `Html.fromHtml`, чтобы создавать только проверенные локальные ссылки и не доверять произвольному HTML/URL модели.

Поддерживаются Markdown-заголовки, жирный текст, inline code, списки и короткие подписи `[описание](message:ID)`; числовые `[ID]` отображаются ссылкой `↗ ID`. `resolve_source_target` разрешает message:/msg:/# либо точный URL, сформированный для исходного peer/ID. Чужая ссылка с тем же номером сообщения не считается источником. Это важно для личных чатов, где одинаковые числа не задают глобальную идентичность сообщения. Неизвестные источники остаются обычной подписью. Открытие источников сохраняет проверку аккаунта, диалога и темы. Копирование/поделиться переводят локальные message:ID в настоящие Telegram URL; числовая подпись Markdown-ссылки не обрабатывается повторно как отдельная цитата. `source_ids` учитывает как числовые ссылки, так и короткие message:ID. Список «Источники» остаётся доступен независимо от качества расстановки ссылок моделью.

Общий renderer применяется даже к результату из одного абзаца: в 3.5.0 ранняя ветка `_result_sections_view` для неразделённого текста возвращала обычный TextView до установки ссылок. Эта ветка больше не используется. При недоступности BottomSheet сохраняется запасной диалог с копированием и отдельным списком источников; полное равенство визуального fallback панели не утверждается.

### Сводка сообщений 3.7.0 — штатные нажатия и облачка с источниками, 27.10.2026

После 3.6.1 владелец повторно сообщил, что значок в шапке и плашка «Непрочитанные сообщения» не работают; на уточнение подтвердил **полное отсутствие реакции**, без уведомления. Это означает, что предыдущие синтетические проверки установки listeners не подтвердили доставку события в конкретном клиенте. Точная причина на телефоне по-прежнему не установлена без данных выполнения. Новая версия меняет путь доставки событий и добавляет точную диагностику; утверждать проверку физического устройства нельзя.

**Русское название.** В видимом интерфейсе «саммари» заменено на «сводка», с согласованием «Сводка готова», «Последняя сводка», «История сводок», «Стиль сводки». Метаданные `__name__` теперь «Сводка сообщений». Стабильный `__id__ = "chat_summary"`, имена ключей и протокол API не меняются, поэтому настройки не требуют переноса. Английские инструкции модели и выбранный пользователем английский язык интерфейса остаются английскими.

**Независимая доставка нажатия.** `SummaryNativeViewHook(MethodHook)` подключается к `android.view.View.performClick` и перегрузкам `performLongClick`. `_native_view_action` сначала проверяет небольшой реестр собственных View по hashCode и точному Java equals. Если элемент не зарегистрирован, original method не подавляется и событие не записывается. Для зарегистрированного элемента собственное действие выполняется через UI-поток, `param.setResult(True)` подавляет старый/заменённый listener. Удержание использует отдельное действие. Защита от двойной доставки в 250 мс предотвращает повтор от вложенного вызова или пары long/short; она не является двухминутным кэшем результата.

Реестр хранит слабую Java-ссылку на View, сильные ссылки на необходимые proxies, owner, обычный и долгий callback. Действия заголовка и плашки принадлежат состоянию чата; действия блоков — конкретному результату. При detach, закрытии результата и выгрузке соответствующие записи удаляются. Если объект исчез, запись удаляется при обращении. Совпадение hashCode чужого View не разрешает выполнение благодаря проверке equals. Вызов выполняет прежние проверки аккаунта/чата/темы; чужой контекст не получает сводку текущего.

Глобальный hook ограничен **нажатиями** и сразу пропускает чужие View. Глобального перехвата всех рисований/касаний нет. Он не получает текст других элементов и не меняет их обработчики. Это всё же более широкий технический перехват framework-метода, чем listener одного элемента; его поддержку в конкретном Android-форке подтверждает диагностика, а не наличие API в справочнике.

`_bind_view_action` включает clickable/enabled до создания SDK-listener. Если Python/Java-адаптер listener не создаётся или не назначается, запись действия остаётся, и native hook способен доставить событие без него. При доступном SDK-listener остаётся прямой запасной путь. В шапке интерактивен весь 48dp `ActionBarMenuItem`; дочерняя иконка non-clickable и больше не создаёт два конкурирующих touch target.

**Установка хуков.** `_hook_java` проверяет возвращённые handle из `hook_all_methods`/`hook_all_constructors`. При отсутствии результата используется перебор `getDeclaredMethods`/`getDeclaredConstructors` самого Class и `hook_method`. Не следует писать «готово» только потому, что обёртка не бросила исключение, когда не получен ни один handle. В безопасный отчёт добавлены количества native click/hold hooks, lifecycle/constructor hooks и зарегистрированных действий, события native_tap/native_hold и успешного подключения плашки. Возможность OnPreDraw proxy теперь не является обязательным условием установки всех остальных UI-хуков.

**Плашка как во втором плагине.** Повторно изучен `ChatUnreadCellConstructorHook` исходного Unread Summary. Важный отсутствовавший запасной путь — `getChildAt(0)`, если private `backgroundLayout` не найден. Новая реализация регистрирует саму ячейку и найденный внутренний элемент, ставит clickable/focusable, учитывает принадлежность корню чата. Post из конструктора может подключить плашку ещё до прикрепления кнопки шапки: root берётся непосредственно у текущего fragment. Для видимых subclass-ячеек используется Java `Class.isInstance`, а не только точное simpleName. Кастомный BadgeTouch больше не забирает DOWN/UP: жесты прокрутки и CANCEL обрабатывает обычный Android/RecyclerListView. **Облачка результата.** `summary_bubbles` разделяет весь ответ по абзацам, пунктам и заголовкам, сохраняет продолжения и весь текст. Каждая зона имеет отдельную карточку. Вся карточка нажимается. Один источник открывается сразу через существующий `_open_source`; несколько — через список только ID этого блока. Копирование всего результата продолжает включать настоящие Telegram URL. Действия блока и ссылки используют тот же native registry, что и исправляемые кнопки. Основные действия панели — повторить, копировать, поделиться, источники, закрыть — также зарегистрированы в нём. При неудачном построении панели временные действия очищаются перед fallback-диалогом.

### Сводка сообщений 3.11.0 — язык, независимые кнопки, цвета, стекло и время повторного открытия

Продолжение 3.10.0. ID плагина остаётся `chat_summary`; настройки подключения и язык ответа сохраняются. Контракт: приложение >=12.5.1, SDK >=1.4.3.3, Python 3.11. На реальном телефоне в этой итерации не запускалось.

Что изменено:

- «Язык интерфейса» перенесён в первую настройку после заголовка: русский, українська, English. Это отдельная настройка от языка ответа AI. При смене языка обновляются также собственные пункты меню чата.
- Независимые переключатели `summary_header`, `summary_menu`, `tap_unread_badge`: кнопка в шапке; оба пункта сводки в ⋮; действие на штатном разделителе непрочитанных. Выключение последнего убирает действие плагина, сам разделитель Telegram остаётся.
- «Посмотреть цвета» показывает те же карточки с текущим дизайном и переключает пять палитр. Выбранная палитра сохраняется. Предпросмотр не читает чат и не обращается к AI. Обычные настройки SDK остаются нативными строками.
- Пятый дизайн «Стекло»: полупрозрачный градиент панели и облачков, тонкая граница. Это прозрачность, без настоящего размытия фона. Непрозрачный текст; запасное обычное оформление при отсутствии API.
- «Анимации облачков»: появление за 180 мс со сдвигом 8 dp; небольшая ограниченная задержка между карточками. Можно выключить. Проверяется системное отключение анимаций Android.
- Время повторного открытия: всегда новая / 30 секунд / 1 / 2 / 5 / 10 / 30 минут / 1 час. По умолчанию 2 минуты, как раньше. Отсчёт от завершения генерации, повторный просмотр время не продлевает. Удержание в шапке по-прежнему запрашивает новую раньше срока. История до пяти результатов на аккаунт остаётся только в RAM и исчезает при выгрузке.
- Метки отправителей заменены с «Участник 1» на `U1`, `U2` и далее. Сохраняется одна метка на личность отправителя и локальная подстановка имён. Поддержаны старые метки в уже готовом результате. Имена внутри текста сообщения не удаляются.

Практика API и новые выводы:

1. Собственные пункты меню регистрируются через `MenuItemData(item_id=..., menu_type=CHAT_ACTION_MENU, ...)`, сохраняется именно возвращённый `add_menu_item` ID. При изменении языка/переключателя удаляются только эти ID через `remove_menu_item`. Повторная синхронизация неизменённого меню не создаёт дубликатов. Неуспешно удалённые ID остаются учтёнными. SDK автоматически очищает свои регистрации при выгрузке. [Plugin class API](https://plugins.exteragram.app/docs/plugin-class).
2. `GradientDrawable.setColors(int[])`, `setOrientation(TL_BR)`, `setCornerRadius`, `setStroke` позволяют сделать мягкий прозрачный фон без изменения alpha всей иерархии. Alpha панели 0.94→0.90, карточки 0.82→0.66. Фон `BottomSheet` становится прозрачным только если градиент панели успешно создан; иначе остаётся обычным. Нельзя выдавать это за аппаратный blur. [Android GradientDrawable](https://developer.android.com/reference/android/graphics/drawable/GradientDrawable#setColors(int[])).
3. `ValueAnimator.areAnimatorsEnabled()` учитывает системную доступность анимаций. Если вызов недоступен, безопаснее показать содержимое сразу. `ViewPropertyAnimator` применяется только к собственным карточкам; отложенный callback проверяет, что плагин активен, view прикреплён и запись действия всё ещё принадлежит тому же владельцу. При закрытии, выключении анимаций и выгрузке выполняются `cancel`, alpha=1 и translationY=0. [Android ValueAnimator](https://developer.android.com/reference/android/animation/ValueAnimator#areAnimatorsEnabled()), [ViewPropertyAnimator](https://developer.android.com/reference/android/view/ViewPropertyAnimator).
4. Таймер открытия хранит `monotonic()` завершения, ключ `(account, dialog_id, thread_id)` и проверяет принадлежность результата истории текущего аккаунта. Максимальное окно кэша — час, максимум 16 ключей; история по-прежнему ограничена пятью результатами на аккаунт. Продление настройки может снова сделать недавний результат доступным, если он ещё в истории. Нулевой срок отключает только автоматическое повторное открытие.
5. Экономию нужно измерять токенизатором, а не длиной имени или числом символов. Проверка на синтетическом JSONL из 230 сообщений, `o200k_base` через [официальный tiktoken](https://github.com/openai/tiktoken): для текста «Встречаемся завтра в 15:00.» имя «Александр Петров» и «Участник 1» дали по 6210 токенов, `U1` — 5520. Имя `Max` — 5290, то есть даже `U1` дороже короткого имени. Это только тестовый фрагмент без системного промпта, а не прогноз стоимости реального запроса; у другого токенизатора результаты отличаются. В длинных сообщениях доля меток ещё меньше. Скрытие имён прежде всего сокращает передачу имён отправителей.
6. В генераторе изменений нельзя заменять `REOPEN_SECONDS =` без привязки к началу строки: совпадение внутри `SUMMARY_REOPEN_SECONDS` может образовать другое допустимое синтаксически имя и вызвать ошибку только при загрузке. AST-проверки синтаксиса недостаточно; добавлен тест полной инициализации тела модуля с заменёнными SDK-импортами.
